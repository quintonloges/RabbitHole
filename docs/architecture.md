# Architecture

Each RabbitHole environment has four containers: Caddy, Next.js, ASP.NET Core and PostgreSQL. Caddy is the only service with a published host port: production uses `127.0.0.1:47831` and development uses `127.0.0.1:47832`. `/api/*` and `/openapi/*` go to the API; all other paths go to Next. The API applies EF migrations before accepting traffic. Database and original documents use separate persistent volumes.

The working checkout defaults to the `rabbithole-dev` Compose project, with development-only configuration, image names, network and volumes. Production retains the original `rabbithole` project and volumes. Its ignored `.local/production/compose.json` captures the effective runtime configuration and pins all four images by SHA-256 ID, with `pull_policy: never` and no build context. The production Caddyfile is a separate copy. Production volumes are external to Compose, so missing volumes fail instead of silently initializing a different library; Compose does not delete external volumes on `down --volumes`. Normal development builds cannot update production. See [environment operations](environments.md) for startup, backups, restore and deliberate releases.

## Data and provenance

Content records retain canonical URL, provider IDs, author, nullable source publication time, ingestion time, excerpt and permitted plain text. Local chapters point to documents and sections. Source text never shares a field with AI synthesis. `ItemIdentities` owns unique, hashed identity keys for URLs, normalized DOIs, arXiv IDs and provider IDs. RSS GUIDs are scoped to a subscription's identity version; changing its feed URL/kind/query starts a new version. Display fields on `ContentItem` are snapshots, not independent uniqueness constraints.

An item has multiple `ItemSources` origins. Disabling one subscription does not suppress an item supplied by another enabled source. Removing or replacing a subscription retains its origin snapshot. Source filters include these historical origins. A bridge between existing records merges them in one transaction: notes, branches, prompts and AI records keep their IDs and point to the oldest surviving item; saved/read/understood flags are combined, progress takes the maximum, and the less restrictive dismissal state wins. Alias records and their original state remain available in exports. Old item links resolve to the survivor; historical edition/evidence references remain intact and editions collapse duplicate aliases on display.

`ItemTopics` separates source assignments, lexical keyword matches, legacy tags with unknown provenance, and explicit user inclusions/exclusions. `ContentItem.TopicIds` is the effective cached projection used by ranking and the UI. User overrides survive refreshes, document retries and keyword edits. The same classifier covers external records and local chapters, without AI. Changing topic keywords or source tags reclassifies the existing catalog.

PostgreSQL forward migrations add the catalog tables and source watch/version fields. Startup then performs an idempotent transactional backfill before serving traffic. The SQLite development path has an additive schema upgrade with equivalent backfill. Existing item, note, state, document, section, trail and practice IDs survive. Previously discarded source associations or overwritten text cannot be reconstructed from the old database; known provider references are recovered where present. Downgrades require restoring a matching pre-upgrade database/uploads backup, because the old schema cannot represent retained aliases and origin versions safely.

User state, notes/highlights, branch nodes, editions and practice attempts are separate rows with foreign keys. Opening records `lastOpenedAt`; read and understood are explicit booleans. Practice responses and self-ratings are evidence of an attempt, not independently verified recall or a mastery score. Topic keywords/preferences are editable; curiosity-only topics are distinct from lasting interests.

Rabbit holes are persistent trees. A node references a real item or a user question; its parent must belong to the same hole. Siblings are retained, duplicate item visits are allowed as distinct nodes, and navigation updates the hole's last-node pointer. Related recommendations use specific concept evidence, adjacent subjects, bounded lexical fallback and source/direction diversity, with actual source IDs for inspection. Free questions are never represented as retrieved publications.

## Ingestion

The API's background service polls enabled due sources with per-source serialization, bounded response sizes, timeouts, conditional requests and exponential backoff. Source edits/deletion share that serialization, preventing a stale refresh from restoring an old query's cursor. Each provider has a separate database context. Upserts are transactional and discard failed tracked changes before persisting retryable health. Adapters normalize RSS/Atom, OpenAlex, arXiv and YouTube channel records. The external HTTP boundary is injectable for deterministic tests.

Interactive OpenAlex searches retain relevance ordering. Watches use native title/abstract scope; an explicit `title:` prefix selects title-only matching. Initial sampling covers the last two years, bounded above by the poll date. Later windows overlap seven days. With an API key, each refresh consumes one bounded cursor page, storing its fixed window and continuation for restart; the checkpoint advances only after the window finishes. Pending pages resume after one minute and failed pages leave progress unchanged. Without a key, only a bounded first-page sample is fetched on the normal schedule, because further cursor pages require authentication. Settings explains that this mode can miss papers; it does not claim exhaustive coverage. Indexing delays longer than the overlap can require an explicit search. arXiv watches preserve documented field and Boolean expressions instead of adding `all:` to structured queries.

RSS text normalization drops script/style/comment content and keeps named Atom authors without concatenating email/URI fields. Manual metadata recognizes author and publication meta tags, never modification or retrieval time as publication. An optional `feedUrl` on URL import retrieves a bounded real feed through the existing safe fetcher and imports only the entry matching the requested canonical URL. Selection scans the entire size-limited XML, including entries after position 100; ordinary refresh parsing remains capped at 100 entries. Direct and autodiscovered feeds share the same fetch, MIME, XML and size protections. It preserves feed provenance without creating a subscription or importing unrelated entries.

Arbitrary user URLs pass public-host, DNS, port, redirect and connect-time IP checks. Metadata-only web import consults robots rules and falls back to a link-only record. Provider embeds are constructed from validated IDs/URLs; returned oEmbed HTML is never injected into the app. No transcript scraping, media downloading or paywall bypassing is involved.

Document uploads are bounded, signature checked and hashed. Parsing runs in a child .NET process with a deadline, GC heap limit, bounded output and one upload at a time. Zip entries are read in memory without extraction, with entry/expansion/path/entity/DRM checks. PDF extraction uses PdfPig; actual pages and available bookmarks become sections. The UI prioritizes bookmark/manual ranges and separates searchable, paginated page records. EPUB sections follow manifest/spine order and EPUB 3 navigation or EPUB 2 NCX anchors within each file. Text is split at actual anchor offsets without duplicating nested TOC entries; leading text is retained. XHTML character entities resolve locally, with external XML resolution disabled and bounded entity expansion. Missing anchors/malformed markup retain readable text with a warning; image-only entries remain accessible in the original. The original remains available on extraction failure. User-defined PDF ranges require all requested extracted pages and add records without deleting page notes/progress.

Interrupted/failed/original-only documents expose Retry extraction; ready books expose Rebuild sections. The retry endpoint and same-hash reupload reuse the document and reconcile sections by locator, preserving IDs, notes, progress, edited metadata and manual ranges. Successful rebuilds order current sections by the parser's reading order. Unmatched old sections are marked `IsSuperseded` and shown under Previous extraction, retaining their text and all references; no reading state is reassigned to new chapter boundaries. PostgreSQL migrations and the additive SQLite upgrade default existing sections to active. Extraction failure keeps prior text and navigation. A missing original is reported explicitly; uploading the same file restores it. Retry and upload share the same import gate.

## Discovery and learning

Daily editions persist ordered item IDs and rationale. Page reloads reuse that selection. A user-requested new selection or more-items action changes it deliberately. Ranking uses explicit topic weights/pins, bounded continuity from saved/explicitly read/liked material and recent user-created turns, feedback, freshness and diversity, with space for candidates outside core interests. Neither AI nor embeddings are required. This is a deterministic heuristic, not a psychological model.

Discover separates the daily edition from topic browsing. Topic/page URL parameters request `/items?topicId=…&dismissed=false&order=reading&limit=30&offset=…`; filtering precedes the total and pagination. Reading order sorts imports by date, grouping each document under its import date and ordering its sections by the persisted section position. It does not regenerate an edition or alter ranking/preferences. Other callers retain the default item ordering.

Item DTOs expose `hasText` independently of whether a list response includes `body`, plus a batched `document` context containing parent title/author, format, section type/position, page bounds/count and superseded status. The projection omits storage paths, upload filenames and full document text. Shared row helpers put the format beside the linked headline and combine provenance, page location and content limitations underneath. Routine availability badges and duplicate reader links are omitted. A supplied source excerpt stays visible, limited to one line on desktop and two on mobile. Generic page/parser titles use the parent title and actual page/section position for display only. Compact **Why this?** uses an accessible native popover with Escape/outside dismissal instead of expanding a feed row.

The curation pass adds a soft per-source daily cap (15%, minimum two, while alternatives exist), near-duplicate title penalties, and a small deterministic rotating boost for items older than 180 days. Unknown publication dates receive no freshness bonus. Related results now prioritize the concept vocabulary described below; lexical phrases remain a fallback for subjects outside that vocabulary. Dismissed and disabled-only records are excluded; broad-topic alternatives are labeled as such and each recommendation cites the starting record. This remains lexical navigation, with no credibility score or claim of semantic certainty.

### Recommendation evidence and concept navigation

`Holes.Origin` and `Nodes.Origin` distinguish `user`, `curated`, `example`, and `legacy-unknown`. Provenance belongs to each turn, so a user can branch from a curated trail without relabeling its earlier nodes. API curators send `origin: curated` or `example` on creation; new nodes inherit a curated/example origin unless a caller explicitly supplies `user`. The interactive UI does so. Navigation does not change provenance or mark anything read. Only the latest 30 user-created turns from the last 30 days contribute a small, transient continuity signal. Opens and understood-only flags add no recommendation continuity. Explicit saves, reads and positive feedback are separately identified; negative feedback never supplies positive exploration evidence.

`Concepts.cs` is a small maintainable vocabulary of phrase aliases and proposed neighboring subjects. It uses title, excerpt, bounded permitted body text and allowlisted subject metadata. Precise expressions such as global workspace and world models avoid single-word workspace/model matches. Long-body matches require repeated non-overlapping mentions and are weaker than title/abstract matches. Concepts are content descriptions, not lasting-interest inferences or credibility judgments. `ContentItem.ConceptTags` and `ExcludedConcepts` hold user overrides separately from source text; arbitrary matching user tags can connect sources across the eight unchanged broad topics. Edit them under **Concepts & tags** in the reader. Overrides survive refresh and merge; explicit inclusions win conflicting exclusions during an identity merge.

Related candidates move through shared concepts, adjacent concepts, concept-family context/phrase matches, then a maximum of two explicitly labeled broad-topic suggestions if fewer than four supported choices exist. Repeated concepts/directions/sources and near-duplicate titles receive bounded selection penalties. Routine-update and announcement patterns receive explainable soft reductions, with explicit item preferences reducing their effect. There is no external discovery or forced filler. `/items/{id}/related?holeId=…` excludes all sources already on that trail, including ancestors and siblings. `includeVisited=true` returns intentional revisits with a `revisit` flag; bounded `visitedIds` supports unsaved path evaluation. IDs are resolved through catalog aliases. The existing short reading-trail endpoint walks the same ranker with exclusions.

Daily `Entries.RationaleJson` stores versioned summary, evidence records (IDs, titles, interaction kinds/concepts/fields), and ranking signals. Discovery rows, Surprise, and branch suggestions share an explanation component; evidence links sit behind **Why this?**, without showing a numerical ranking dashboard. Format heuristics express a preference for explanatory/research formats, not objective intellectual quality. User topic settings remain the strongest signal. Edition order and evidence persist across reloads. Legacy entries retain their original strings/IDs in exports; the UI never repeats unrecorded exploration claims. At the recommendation-evidence upgrade only, the active legacy edition's day key was archived with its ID, preserving every entry; the next normal request created one current edition with recorded evidence.

The additive PostgreSQL migration `20261018041856_RecommendationEvidence` and SQLite upgrade add these fields. An idempotent backfill identifies only the two audited curated trail IDs and their original creation-window nodes (see the curation report); other old origins remain unknown. It does not infer provenance from titles or reset personal state. Export version 3 includes the added fields. Use a matching database/uploads backup to return to earlier code. The reproducible frozen-catalog evaluation and actual migration/state-preservation results are in [recommendation-quality-report.md](recommendation-quality-report.md).

Human-editable source/reading packs under `config/` are opt-in tooling, not startup seed data. The Python installers use the ordinary API, match source identities or item identifiers (including known provider aliases), preserve existing preferences, and leave unverified new sources disabled. The reading installer resolves aliases before an import can overwrite edited metadata. Existing-source refresh failures produce visible errors and a nonzero installer exit code. The audited live outcome is in [feed-curation-report.md](feed-curation-report.md).

PostgreSQL GIN indexes support title/excerpt/body search and note search. Partial lexical matching handles short terms; SQLite integration tests use a lexical fallback. Related items and short reading sequences use records already present in the catalog.

Reflection prompts reference selected records and available source passages. Again/Hard/Good/Easy adjust a simple review interval/ease value; Not now moves the due time without a review credit. Optional AI critique is separate from this self-report. There are no execution sandboxes for user code because engineering practice is text reasoning only.

Practice drafts and asynchronous critique results belong to individual prompts; snoozing another prompt cannot submit or erase the active draft. Item actions notify parent caches only after persistence succeeds. Local optimistic controls roll back on failure.

The item route keys each reader session by item ID. Note drafts and selected quotations use item-specific browser session storage; late asynchronous responses cannot populate another item's editor or results. Saved notes still come from the API. The reading surface precedes Notes/Explore/Details tools, with adjacent document navigation above and below and a bounded Contents dialog. PDF display reflows extraction whitespace while retaining words and blank-line paragraph boundaries; it does not rewrite stored source text or remove line-ending hyphens. A per-document browser-session preference restores original line breaks. Selection tools accept only selections wholly inside the source body, and quote validation continues against the stored source using the API's existing whitespace normalization.

## Optional AI

The server reads endpoint/model/key from private environment configuration. AI is off until enabled in Settings, and no background enrichment runs. An explicit action sends at most two 6,000-character source passages plus a bounded user response. One request runs at a time, with six actions/minute, bounded tokens, deadline, one conservative retry and a content/model-specific cache.

Responses must parse as structured JSON and reference supplied IDs. Unknown citations, unsupported URLs and invalid quoted passages are rejected. Source data is framed as untrusted evidence. The provider has no tools and cannot fetch/import/delete anything. Structural checks cannot establish the truth of generated prose; the UI labels it synthesis and retains original sources for comparison.

## Validation boundaries

xUnit tests exercise the real relational services with SQLite and fixture HTTP. The E2E host runs the actual API over Kestrel and the actual Next UI. It is a separate project, never compiled into the production application. Docker smoke checks exercise PostgreSQL migrations, full-text search, real provider imports and persistence separately. The acceptance report records what actually ran.
